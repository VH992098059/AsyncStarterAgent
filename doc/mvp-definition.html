项目愿景与核心价值

核心愿景：消除冷启动摩擦力

每一次面对空白文档的瞬间，都是一次认知资源的消耗。心理学研究揭示了两个关键机制：蔡格尼克效应表明，未完成的任务会在大脑中持续占据工作记忆空间，而"从零开始"正是最极端的未完成状态；启动成本理论指出，任务启动阶段所需的认知负荷远高于后续执行阶段，人类大脑在"启动"和"惯性运行"两种模式之间切换时，会产生显著的心理阻力。

Async Starter Agent 的核心愿景，就是将用户从"冷启动"的焦虑中彻底解放。当用户意识到需要完成一项文档任务时，Agent 已经在后台完成了信息搜集、框架搭建和草稿生成。用户不再是"面对白纸的创作者"，而是"站在已有基础上的审查者和完善者"——从 0 到 1 的心理鸿沟，被 Agent 填平为从 30% 到 100% 的渐进式完善。

产品定位声明：Async Starter Agent 是一款面向知识工作者的异步文档助手，通过事件驱动的后台 Agent 自动搜集个人上下文并生成文档草稿，消除"冷启动摩擦力"，让用户从零创作者变为高效审查者。

事件驱动的后台异步 Agent

Agent 不依赖用户主动发起请求，而是持续监听用户工作环境中的事件信号——任务创建、DDL 临近、笔记更新等。一旦检测到触发条件，Agent 在后台自动启动工作流，无需用户等待或干预，实现真正的"零摩擦"启动体验。

个人上下文 RAG

通过检索增强生成（RAG）技术，Agent 能够从用户的 GitHub 提交记录、日历事件、IM 沟通记录、个人笔记等多源数据中提取与当前任务高度相关的上下文信息。这些信息经过向量化索引和语义检索，确保生成的草稿不仅格式正确，更包含用户真实的工作内容和项目细节。

自动化文档工作流

从触发到交付的完整工作流自动化：Agent 自动选择合适的文档模板，将搜集到的上下文信息填充到模板结构中，通过 LLM 生成连贯的草稿内容，标记需要用户决策的待补充位置，最终将完成的草稿交付到用户指定的文档平台（Notion/Obsidian），形成闭环。

核心价值量化

用户只需扮演"审查者"和"修改者"，而非"从零开始的创作者"。Agent 在后台默默完成信息搜集、框架搭建和草稿生成，将任务启动成本降低 70%。草稿完成度达到 30% 以上，意味着用户面对的不再是空白页面，而是一个有结构、有内容、可修改的半成品。

MVP 范围定义

IN

MVP 包含

关键词触发

支持前缀匹配模式（"写..."、"准备..."、"规划..."、"整理..."）和包含匹配模式（任务描述中包含"周报"、"总结"、"纪要"等关键词）。匹配规则可配置，支持正则表达式扩展。

DDL 触发

检测任务管理工具中的截止日期，默认在 DDL 前 24 小时自动触发准备流程。提前量可配置（12h/24h/48h），支持按任务优先级差异化配置提前量。

GitHub 适配

通过 GitHub REST API / GraphQL API 拉取用户关联仓库的 commits（含 message 和 diff 摘要）、Pull Requests（标题/描述/状态）、Issues（状态变更/评论）和 Code Reviews（评审意见）。

日历适配

支持 Google Calendar 和 Outlook Calendar，通过 OAuth2 授权拉取指定时间范围内的日历事件，提取会议主题、参会人列表、会议时间和时长等结构化信息。

IM 适配

拉取用户在飞书/Slack 中发送的消息、标记为待办的讨论帖、以及订阅频道的每日摘要。通过关键词过滤和时间窗口限定，仅提取与当前任务相关的沟通内容。

笔记适配

Obsidian 通过本地文件系统监听 vault 目录变更（fsnotify），读取 Markdown 文件内容；Notion 通过官方 API 读取指定数据库和页面。两者差异：Obsidian 为本地实时监听，Notion 为 API 轮询（间隔可配置）。

模板引擎

内置周报、项目总结、会议纪要、规划方案四类模板，采用 YAML Front Matter + Markdown 正文格式。模板支持变量插值（如 {{date_range}}、{{project_name}}）和条件区块。

LLM 草稿生成

采用"骨架+填充"策略：先根据模板生成文档骨架（章节标题、列表结构），再基于 RAG 检索的上下文填充具体内容，控制完成度在 30-40%。MVP 阶段使用 GPT-4o / Claude 3.5 Sonnet 作为生成模型。

[待补充] 标记

在草稿中标记需要用户决策或补充信息的位置。标记逻辑：当 LLM 缺乏足够上下文生成确定性内容时（置信度低于阈值），自动插入 [待补充] 标记并附带提示说明（如"[待补充: 请确认Q2目标数据]"）。

Notion 交付

通过 Notion API 将草稿写入用户指定的 Database 或 Page 下，自动创建页面层级结构（标题/正文/待补充区块），保留 Markdown 格式并转换为 Notion Block 格式。

SSE 流式输出

后端通过 Server-Sent Events 推送生成进度，前端通过 EventSource API 消费。SSE 事件类型包括：status（阶段状态更新）、chunk（文本片段）、complete（生成完成）、error（异常信息），实现实时流式渲染。

OUT

MVP 不包含

语音唤醒

排除原因：语音交互涉及 ASR 准确率、噪声环境处理等复杂技术问题，且 MVP 目标用户主要为桌面端知识工作者，文本触发已满足核心场景。预计纳入：MVP 后第 2 个迭代。

移动端推送

排除原因：移动端推送需要 APNs/FCM 集成、移动端 UI 适配，且 MVP 阶段 SSE + 桌面通知已能覆盖"草稿就绪提醒"场景。预计纳入：MVP 后第 1 个迭代。

多用户协作

排除原因：协作功能需要权限系统、实时同步、冲突解决等基础设施，架构复杂度远超 MVP 范围。MVP 聚焦单用户场景验证核心价值。预计纳入：V2.0。

自定义 Prompt 编辑器

排除原因：Prompt 编辑器需要代码编辑器组件、语法高亮、变量提示等 UI 基础设施，且 MVP 阶段内置模板已覆盖核心场景，用户自定义需求需通过用户反馈验证。预计纳入：V1.5。

数据分析报表

排除原因：数据分析需要数据仓库、ETL 管道和可视化组件，属于增值功能而非核心链路。MVP 需先验证"草稿生成"的核心价值，再考虑分析能力。预计纳入：V2.0。

说明：以上功能将在后续迭代中根据用户反馈和优先级评估逐步纳入。MVP 阶段聚焦于核心链路的打通和验证，确保"触发-搜集-生成-交付"的端到端流程可用。

核心用户故事

01

关键词触发周报

触发条件

用户在 Todoist 创建新任务，标题为"写本周周报"，关键词"周报"命中触发规则

Agent 行为

1) 识别触发类型为"周报" 2) 确定时间范围为本周一至今 3) 并行拉取 GitHub commits/PRs、日历事件、Slack 关键消息 4) 选择周报模板 5) 通过 LLM 生成草稿 6) 标记待补充位置

用户操作

收到桌面通知"周报草稿已生成"，打开草稿页面，审阅各章节内容，修改不准确之处，补充[待补充]标记位置的细节信息

预期结果

从创建任务到收到草稿通知不超过 30 秒，草稿包含本周工作摘要、关键进展、下周计划三部分，完成度约 35%

成功标准

用户修改时间 < 10 分钟，修改率 < 50%，最终文档包含至少 3 个数据源的信息

02

DDL 触发规划

触发条件

用户在任务管理工具中设定的"Q2 规划文档"截止日期为周五，系统在周四上午自动检测到 DDL 临近（提前 24h）

Agent 行为

1) 检测到 DDL 触发 2) 拉取本周未完成的任务列表 3) 搜集下周日历中的会议和里程碑 4) 从笔记中检索相关规划素材 5) 选择规划模板 6) 生成包含"本周回顾+下周计划"的草稿

用户操作

收到通知"下周规划草稿已准备"，打开草稿，确认未完成事项是否需要顺延，补充下周重点目标的量化指标，调整优先级排序

预期结果

草稿自动归类本周已完成/未完成事项，下周计划基于日历事件生成时间线框架，完成度约 30%

成功标准

DDL 触发准确率 100%，草稿在 DDL 前 24h 准时生成，未完成事项无遗漏

03

笔记触发会议纪要

触发条件

用户在 Obsidian vault 中新建笔记，文件名包含"会议"或标签包含 #meeting，Agent 通过 fsnotify 检测到文件创建事件

Agent 行为

1) 识别触发类型为"会议纪要" 2) 从日历查找最近 24h 内的会议事件 3) 提取会议主题、参会人、时间 4) 从飞书/Slack 检索相关讨论 5) 生成结构化纪要模板（议题/讨论/决策/行动项）

用户操作

在 Obsidian 中看到自动补充的会议背景信息，填写讨论内容和决策要点，确认行动项的负责人和截止日期

预期结果

笔记自动填充会议元信息（主题/参会人/时间），生成"议题-讨论-决策-行动项"四段式模板，完成度约 35%

成功标准

日历关联准确率 > 90%，参会人信息无遗漏，模板结构完整

04

草稿审查与交付

触发条件

Agent 完成草稿生成后，通过桌面通知提醒用户"周报草稿已就绪，点击查看"

Agent 行为

1) 推送草稿就绪通知 2) 在编辑器中打开草稿，高亮[待补充]标记位置 3) 用户修改后检测变更 4) 确认交付后，通过 Notion API 创建页面并写入内容 5) 返回交付确认和页面链接

用户操作

点击通知打开草稿，逐段审阅，修改不准确的内容，补充[待补充]位置，点击"确认交付"按钮，选择目标 Notion 页面位置

预期结果

草稿自动同步到 Notion 指定位置，保留格式和层级结构，[待补充]标记转为 Notion Callout Block 提醒，交付过程无需手动复制粘贴

成功标准

Notion 写入成功率 > 99%，格式保真度 > 95%，交付耗时 < 5 秒

05

实时状态监控

触发条件

用户主动打开 Agent 状态面板，或 Agent 开始执行任务时自动弹出进度窗口

Agent 行为

1) 通过 SSE 推送各阶段状态（触发确认/数据搜集/模板选择/草稿生成/交付就绪）2) 实时推送 LLM 生成的文本片段 3) 显示各数据源的搜集进度 4) 异常时推送错误信息和重试状态

用户操作

在状态面板中实时观察 Agent 工作进度，看到数据搜集阶段拉取了哪些数据源，草稿逐步生成（文字逐字出现），无需等待全部完成即可开始审阅已生成部分

预期结果

状态面板实时更新，SSE 延迟 < 200ms，草稿文字流式渲染无卡顿，各阶段状态转换清晰可见

成功标准

SSE 连接稳定性 > 99.5%，首字节延迟 < 3 秒，用户可感知到实时进度更新

功能模块划分

触发引擎

Trigger Engine

关键词匹配

输入：任务标题/描述文本

处理：正则匹配预定义关键词模式，支持前缀（"写..."）和包含（"周报"）两种模式，匹配后映射到对应文档类型

输出：触发事件（含文档类型、时间范围、优先级）

DDL 检测

输入：任务管理工具中的截止日期字段

处理：定时轮询（每 30 分钟）检查即将到期的任务，计算当前时间与 DDL 的差值，匹配提前量配置

输出：DDL 触发事件（含任务信息、剩余时间、建议文档类型）

文件变更监听

输入：Obsidian vault 目录的文件系统事件

处理：通过 fsnotify 监听文件创建/修改事件，解析文件名和标签判断文档类型

输出：文件触发事件（含文件路径、文档类型、变更类型）

上下文搜集器

Context Collector

GitHub 适配器

通过 GitHub REST API v4 拉取数据。使用 GraphQL 批量查询减少 API 调用次数，按时间范围过滤 commits/PRs/issues/reviews，结果缓存至本地 SQLite（TTL 5 分钟）。

日历适配器

Google Calendar 使用 Calendar API v3 + OAuth2 授权，Outlook 使用 Microsoft Graph API。拉取指定时间范围的 events 资源，提取 summary/attendees/start/end 字段。

IM 适配器

飞书通过开放平台 API v2 拉取消息列表，Slack 通过 Web API + Bolt SDK。支持关键词过滤和时间窗口限定，仅提取与触发任务相关的消息线程。

笔记适配器

Obsidian 通过 fsnotify 监听本地 vault 目录变更，直接读取 Markdown 文件；Notion 通过官方 API v1 的 search/databases/query 端点检索相关页面，支持全文搜索和属性过滤。

草稿生成器

Draft Generator

模板选择与变量插值

根据触发事件类型自动匹配模板，将触发元数据（日期范围、项目名等）注入模板变量，生成初始骨架文档。

RAG 上下文注入

将搜集到的多源上下文向量化后检索与模板各章节最相关的内容片段，按章节组织后注入生成 Prompt。

[待补充] 标记生成

LLM 输出后处理阶段，检测低置信度内容（通过 logprob 或结构化输出判断），自动插入标记和提示说明。

Eino 编排的 5 阶段 DAG

使用 Eino 框架编排生成流水线：Stage1 模板解析 → Stage2 上下文检索 → Stage3 骨架生成 → Stage4 内容填充 → Stage5 标记与校验。各阶段可独立重试，支持断点续生成。

交付管道

Delivery Pipeline

Notion API 写入

通过 Notion API v1 的 pages/create 端点创建页面，使用 blocks/children/append 追加内容块。Markdown 转 Notion Block 格式，[待补充]标记转为 Callout Block。

Obsidian 文件写入

直接写入用户 vault 目录下的指定路径，保留 Markdown 格式，[待补充]标记使用 Obsidian Callout 语法（> [!warning] 待补充）。

SSE 流式通知

草稿就绪后通过 SSE 推送 complete 事件，包含草稿 ID 和预览链接。前端 EventSource 监听后触发桌面通知（Web Notification API）。

Notion AI

通用 AI 写作助手，嵌入 Notion 编辑器中。用户需手动触发 AI 功能，AI 仅基于当前页面内容生成文本，不自动搜集外部上下文数据。适合通用写作场景，但无法实现"零摩擦"的自动化文档生成。

GitHub Copilot

代码补全和生成工具，基于当前文件和项目上下文提供建议。聚焦于代码场景，不生成文档草稿（周报/总结/纪要），也不跨数据源搜集上下文。是代码领域的效率工具，但无法解决文档冷启动问题。

Reclaim.ai

智能日程管理工具，自动为任务分配时间块、调整日历安排。聚焦于时间管理而非内容生成，不生成文档草稿，仅基于日历数据工作。解决了"时间安排"问题，但未解决"内容创作"的冷启动问题。

我们的差异化优势

事件驱动 + 自动触发

无需用户主动发起，Agent 在检测到触发条件后自动启动工作流，实现真正的零摩擦体验。

多源个人上下文 RAG

跨 GitHub/日历/IM/笔记四大数据源搜集上下文，生成的草稿包含用户真实的工作内容，而非通用模板填充。

端到端闭环交付

从触发到交付的完整闭环，草稿自动写入 Notion/Obsidian，无需手动复制粘贴，形成文档工作流的自动化闭环。

MVP 成功指标

草稿完成度目标
≥30%

测量方法：统计 Agent 生成的文本 token 数占最终交付文档 token 数的比例。"完成"定义为：章节结构完整、关键数据已填充、仅剩细节需要用户补充。排除[待补充]标记位置的内容。

用户修改率目标
<50%

计算方法：修改率 = 用户修改的文本段落数 / 草稿总段落数。修改包括：内容重写、数据更正、删除冗余段落。不包括：格式调整、[待补充]位置填充。修改率越低说明草稿质量越高。

端到端延迟目标
<30秒

各阶段时间分配：触发确认 <1s，上下文搜集 5-10s（并行拉取），模板选择 <1s，LLM 生成 10-15s（流式输出），交付写入 2-3s。SSE 首字节延迟 <3s，用户可在生成过程中开始审阅。

数据源覆盖率目标
≥3个
GH
Cal
IM
Note

优先级排序：1) GitHub（开发者核心数据源）2) 日历（会议/日程信息）3) IM（沟通上下文）4) 笔记（个人知识库）。MVP 至少接入前 3 个，笔记适配器作为增强项。

用户满意度目标
≥4.0/ 5.0

评分维度：1) 草稿内容相关性（是否包含真实工作内容）2) 草稿结构完整性（章节是否齐全）3) 交互体验流畅度（触发到交付的流程是否顺畅）4) 时间节省感知（相比手动撰写的效率提升）。收集方式：每次交付后弹出 1-5 分评分弹窗 + 可选文字反馈。

前端方案

方案一: Tauri + Lobe UI

Rust 后端 + React 前端，原生桌面体验，Lobe UI 提供聊天式交互组件。优势：轻量、性能好、原生系统集成度高。适合桌面端优先策略。

方案二: Flutter

跨平台框架，一套代码覆盖桌面+移动端。优势：移动端扩展成本低。劣势：桌面端原生体验不如 Tauri，包体积较大。

MVP 推荐：方案一（Tauri + Lobe UI），桌面端优先验证核心价值。

数据存储

向量数据库

PostgreSQL + pgvector，存储用户上下文的向量化表示，支持语义检索和相似度匹配，用于 RAG 上下文注入。与业务数据同库管理，减少运维复杂度。

关系型数据库

PostgreSQL，存储用户配置、触发规则、任务状态、草稿元数据等结构化数据，通过 GORM 操作。

文件系统

本地文件系统，存储 Obsidian vault 的 Markdown 文件、模板文件、LLM 生成的草稿缓存。

部署方案

MVP: Docker 单机部署

使用 Docker Compose 编排所有服务（API Server / Worker / PostgreSQL + pgvector / Redis），单机运行，适合个人用户和早期验证。

V2.0: K8s 集群部署

迁移到 Kubernetes 集群，支持水平扩展、自动伸缩、滚动更新。引入 Ingress + Service Mesh，支持多租户隔离和企业级部署。
