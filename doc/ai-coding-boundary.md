## 0. 一句话原则

> **不超出规范、不自我发挥、有想法先问、问完再动。**

## 1. 核心边界（红线 / 硬性禁止）

下列行为**严禁执行**，违反任何一条都需要立即回退并向用户说明：

### 1.1 需求层面

| # | 红线 | 含义 |
| --- | --- | --- |
| R1 | **禁止超出 `requirement-spec.html` / `mvp-definition.html` 范围** | 任何 FR- 编号外的功能一律不实现 |
| R2 | **禁止自我想象 / 自创功能** | 规范没说就不做，不要"顺便加个 XX" |
| R3 | **禁止修改 P0 需求的验收标准** | 验收标准在 `requirement-spec.html` 中已锁定 |
| R4 | **禁止跨 Phase 提前实现** | Phase 1 没结束，不写 Phase 2 的代码 |
| R5 | **禁止把 OUT 档功能当 MVP 实现** | V1.5/V2.0 的功能不写 |
| R6 | **禁止改 5 个用户故事** | US-01~05 是 MVP 验收基准，不可增删 |

### 1.2 代码层面

| # | 红线 | 含义 |
| --- | --- | --- |
| C1 | **禁止写占位符代码** | 不允许 `TODO` / `FIXME` / `TBD` / `// 后面补` 之类 |
| C2 | **禁止删已有代码未经确认** | 即使是看似无用代码，删除前必须问 |
| C3 | **禁止改文件路径已定的接口** | API 路径、数据表名、字段名改前必问 |
| C4 | **禁止在代码中留调试输出** | `fmt.Println` / `console.log` 调试语句需清理 |
| C5 | **禁止绕过错误处理** | 不能用 `_ = err` 吞掉错误 |
| C6 | **禁止硬编码密钥/Token** | 任何敏感信息走环境变量 |
| C7 | **禁止用未声明的依赖** | 新增 `go.mod` / `package.json` 依赖前必问 |
| C8 | **禁止写 mock 数据** | 不允许硬编码模拟数据、伪造返回值、写 mock 适配层；所有数据必须走真实接口/数据库，测试中需要隔离时用接口抽象 + 依赖注入，严禁为赶进度写 mock 数据占位 |
| C9 | **禁止使用 npm / yarn 安装前端依赖** | 前端包管理器仅限 `pnpm`（优先）或 `bun`，严禁使用 `npm install` / `npm add` / `yarn add` 等命令 |
| C10 | **禁止使用 emoji** | 代码、注释、文档、日志输出、UI 文本中严禁使用任何 emoji 表情符号 |

### 1.3 流程层面

| # | 红线 | 含义 |
| --- | --- | --- |
| P1 | **禁止 `git commit` 未经用户允许** | 改动完先展示 diff，由用户决定是否提交 |
| P2 | **禁止 `git push`** | 永远不主动 push 到远程 |
| P3 | **禁止执行破坏性命令** | `rm -rf` / `drop table` / `git reset --hard` 等需用户明示 |
| P4 | **禁止跳过测试** | TDD 是底线，未写测试不写实现 |
| P5 | **禁止不读就改** | 改任何文件前必须先用 `Read` 读完整 |
| P6 | **禁止长篇未经请求的代码** | 单次改动控制在可审查范围（建议 < 300 行） |
| P7 | **禁止带偏移继续编码** | 编码过程中发现实现已偏离当前任务 / 需求 / 范围 / MVP，必须立即停止并按 §3 询问，不允许"先这样稍后再调"（详见 §8.8） |

## 2. 必须执行（MUST DO）

每次编码活动都必须遵守：

| # | 规则 | 操作 |
| --- | --- | --- |
| M1 | **改动前先读** | 用 `Read` / `Grep` / `Glob` 摸清现状 |
| M2 | **先规划再编码** | 用 `TodoWrite` 列出步骤，完成一项勾一项 |
| M3 | **TDD** | 写测试 → 跑测试确认失败 → 写实现 → 跑测试确认通过 |
| M4 | **引用来源** | 写代码时引用具体规范条款（"按 FR-B01 实现"） |
| M5 | **跑完测试再交付** | 改动完必须执行测试命令并展示结果 |
| M6 | **小步提交** | 每个原子改动单独一个 diff，不打包提交 |
| M7 | **保持类型/命名一致** | 跨文件使用已在规范中定义过的类型与字段名 |
| M8 | **依赖使用最新稳定版** | Go 依赖一律 `go get <pkg>@latest`（不锁版本到具体 tag）；前端组件包一律 `pnpm add <pkg>@latest`（优先使用 pnpm，备选 `bun add <pkg>@latest`），严禁使用 npm / yarn。排除 pre-release (alpha/beta/rc)；每次升级后必须跑测试验证；**major 版本号（major bump）变化时必须在 [decision-log.md](./decision-log.md) 记录原因与影响**。当计划文件（plans/*.md）锁定了具体版本时，M8 优先 |
| M9 | **持续对齐检查** | 每完成一个原子改动（文件 / 函数 / commit / todo）必须自问 3 问：① 这段代码对应哪条任务 / FR / Story？② 在 MVP / 范围 IN-OUT 矩阵内吗？③ 有没有"顺手加"规范没有的东西？任一答不上 / 答否 → 立即停止 + AskUserQuestion（详见 §8.8） |

## 3. 必须询问（MUST ASK）

遇到以下**任意一种情况**必须用 `AskUserQuestion` 暂停并询问，得到明确答复后才能继续：

### 3.1 规范不明确

- 规范中只描述了**输入/输出**但没说**实现方式**（如 FR-C03 没说用什么 prompt 模板）
- 规范中**验收标准**有歧义（"准确率 > 85%" 的测量方式）
- 规范中**字段定义**有缺漏（Draft 表没定义 `task_id` 关联字段）

### 3.2 需要自决

- 多个合法实现路径（如缓存用 Redis 还是内存 map）
- 包/库选型（"Go 里有 zap / zerolog / logrus 三选一"）
- 错误处理策略选择（"返回 error 还是 panic"）
- 性能 vs 复杂度权衡

### 3.3 涉及改动现有代码

- 发现现有代码**与规范不一致**（如命名风格不同、缺测试）
- 需要**重构**已有代码以支持新需求
- 现有代码**存在 bug** 但不是当前任务范围

### 3.4 范围扩展

- 觉得"这里应该加个 XX"（即使听起来很合理）
- 想优化非任务范围的代码
- 想顺便补个文档/注释

### 3.5 外部依赖

- 需要新增第三方库
- 需要调用未在 `requirement-spec.html` 第 8 节列出的外部 API
- 需要修改技术栈选型（Tauri → Flutter 等）

### 3.6 不可逆操作

- 删除文件 / 目录
- 数据库 schema 变更（特别是生产数据）
- 修改 `go.mod` / `package.json` 版本约束
- 修改 CI/CD 配置

## 4. 询问模板（强制格式）

每次询问必须按以下格式，让用户能快速决策：

```markdown
## 🤔 边界问题：[简短标题]

**触发场景**：[在做哪件事时遇到的问题]
**当前位置**：[文件路径:行号 或 阶段/任务]
**规范对应**：[FR-XX 或 NFR-XX，或"无对应"]

### 现状
[代码片段或规范原文]

### 我的建议（仅供决策参考）
[选项 A / 选项 B / 选项 C]

### 不建议
[为什么不能完全按规范来]

**请选择**：
- A. 按建议 A 实现
- B. 按建议 B 实现
- C. 其它（请说明）
```

```markdown
## [YYYY-MM-DD HH:MM] 决策 #N

**问题**：[触发问题]
**用户回复**：[原话引用]
**执行方案**：[具体怎么改]
**影响范围**：[文件 / 阶段 / 后续任务]
```

文件路径：`doc/decision-log.md`（首次需创建）

## 6. 边界触发后的标准动作

```
触发边界情况
   │
   ▼
立即停止当前编辑
   │
   ▼
用 AskUserQuestion 询问（按 §4 模板）
   │
   ├── 用户同意 → 继续执行 + 追加 ADR
   │
   ├── 用户拒绝 → 回退到上一个安全状态
   │
   └── 用户说"你自己决定" → 记录到 ADR 后继续（但仅限非红线场景）
```

**严禁**用"先做了再说" / "反正可以回退" 之类的侥幸心理。

## 7. 边界清单速查

### 7.1 ✅ 可以直接做的

- 按 FR- 编号实现对应功能
- 按 task-tracker.html 的任务清单执行
- 添加测试用例
- 修复**当前任务范围内**的 bug

- 超出 20 项 FR 范围
- 写 TODO/占位符
- 提交未经允许的代码
- 自我发挥加功能
- 删用户代码未经确认

- 跳过 TDD

## 8. Superpower Skills 使用规范

### 8.1 核心原则

> **凡是可被 Skill 增强的场景，必须先调用 Skill 再动手编码；Skill prompt 展开前不得开始实质性工作。**

AI 编码助手应将 Skill 视为**第一性资源**——Skill 是经过蒸馏的领域最佳实践与流程约束，**通用 LLM 能力永远不应替代专用 Skill**。

### 8.2 何时必须调用 Skill

| # | 触发场景 | 必调 Skill（按顺序） |
| --- | --- | --- |
| S-T1 | **任何对话开始** | `using-superpowers`（建立 Skill 查找基础） |
| S-T2 | **任何创意 / 设计 / 新功能 / 改行为** | `brainstorming`（写代码前先探索意图与设计） |
| S-T3 | **复杂 Bug / 测试失败 / 异常行为** | `systematic-debugging` → `TRAE-debugger`（需要运行时证据时） |
| S-T4 | **任何功能 / 修复的实现** | `test-driven-development`（TDD 是底线） |
| S-T5 | **任务有 ≥ 3 个步骤或需多窗口推进** | `TodoWrite`（必写）+ `writing-plans`（多步时） |
| S-T6 | **执行预先写好的实现计划** | `executing-plans` 或 `subagent-driven-development` |
| S-T7 | **2+ 独立任务可并行、互不依赖** | `dispatching-parallel-agents` |
| S-T8 | **创建 / 优化 Skill** | `skill-creator` → `writing-skills` |
| S-T9 | **完成实现 / 声称"做完了"之前** | `verification-before-completion` |
| S-T10 | **提交代码审查 / 接收审查反馈** | `requesting-code-review` / `receiving-code-review` |
| S-T11 | **安全敏感代码（auth / 密钥 / 输入校验）** | `TRAE-security-review` |
| S-T12 | **需要隔离工作区再做** | `using-git-worktrees` |
| S-T13 | **前端设计 / UI 实现 / 页面开发 / 样式调整** | `design-taste-frontend` / `gpt-taste` / `high-end-visual-design` / `stitch-design-taste`（根据场景选择对应 taste 类 Skill，禁止跳过直接写样式） |

**判定口诀**："看到任务 → 脑内匹配 Skill → 有匹配的先调 → 没匹配的再问"。

**没匹配到怎么办？**
- 先用 `find-skills` 工具查
- 查不到才考虑不调，但要把"未调 Skill 的理由"记到 ADR

### 8.3 标准工作流（按时间顺序）

```
using-superpowers               → 基础：会找会用 Skill
        ↓
brainstorming（创意 / 设计时）    → 探索意图、约束、设计
        ↓
writing-plans（多步时）           → 形成可执行计划
        ↓
test-driven-development         → 写测试 → 跑失败 → 写实现 → 跑通过
        ↓
verification-before-completion  → 跑测试 + lint + diff 自查
        ↓
requesting-code-review          → 提交前自审 / 接收反馈后按 receiving-code-review 走
```

**简版（单步小改）**：`using-superpowers` → `test-driven-development` → `verification-before-completion`。

### 8.4 红线（Skill 层面）

| # | 红线 | 含义 |
| --- | --- | --- |
| SP1 | **禁止跳过 Skill 直接动手** | 见到任务就写代码 = 违反 §8.2 |
| SP2 | **禁止用通用能力替代专用 Skill** | 例如不调 `brainstorming` 就直接做创意设计 |
| SP3 | **禁止在 Skill prompt 展开前先回话** | 必须等 Skill 完整加载再继续 |
| SP4 | **禁止忽略 Skill 输出的"应当询问"提示** | Skill 经常强制 AskUserQuestion，跳过 = 同时违反 §3 |
| SP5 | **禁止"懒得调"** | 没有 100% 把握 Skill 不相关时，**倾向调用而非不调用**；按"调用错了浪费一次加载"而非"漏调导致方向跑偏"算账 |
| SP6 | **禁止前端设计跳过 taste Skill** | 前端页面/组件/样式开发必须先调用对应 taste 类 Skill（design-taste-frontend / gpt-taste 等），严禁直接手写 CSS/组件导致 generic AI slop 风格 |

### 8.5 与现有规范的关系

| 关系 | 协同方式 |
| --- | --- |
| §1.2 C1（不写占位符） | TDD Skill 强制先写测试，避免 TODO |
| §1.2 C8（不写 mock） | verification Skill 强调真实数据验证 |
| §2 M1-M3（读 / 规划 / TDD） | 是 Skill 流程的子集 + 强化版 |
| §3（必须询问） | Skill 经常触发 AskUserQuestion；用 §4 模板 |
| §5（ADR） | Skill 决策、Skill 加载失败、新增 Skill 都要落库 |
| §9（违规处理） | 违反 §8 触发 §9 标准动作 |

### 8.6 自检清单（每轮收尾前自问）

- [ ] 本轮开始时是否调过 `using-superpowers`？
- [ ] 涉及创意 / 设计的部分是否调过 `brainstorming`？
- [ ] 实现前是否写过**失败**的测试？
- [ ] 完成前是否跑过测试 + lint + 看 diff？
- [ ] 有没有"该调但没调"的 Skill？（凭直觉答：通常有 → 调）

### 8.7 何时**不**调用 Skill

- 用户**显式**说"不用 Skill，直接 XX" → 记录到 ADR 后执行（不重复发问）
- Skill 加载失败且**非关键** → 记录到 ADR 后继续；下次重试
- 当前任务 / 需求 / 范围明确**不在范围内**的工作 → 不调相关 Skill（无需求时 brainstorming 也无意义）
- 单纯查文档 / 读文件 / 跑已有命令 → 不需要 Skill 包装

### 8.8 持续对齐机制（项目无关 / 可移植）

> **适用范围**：本节是**通用工程纪律**，不引用任何具体项目文件名 / 业务术语，可平移到**任何**项目。  
> **核心命令**：每完成一个原子改动，立即把已实现的功能与"任务 / 需求 / 范围"三方对比；发现任何偏移 → **立即停止** + 按 §3 询问；不要"先这样稍后再调"。

#### 8.8.1 三个对比维度（任何项目都成立）

| # | 维度 | 通用含义 | 在你项目里的映射示例（**仅作示例，可任意替换**） |
| --- | --- | --- | --- |
| D1 | **任务** | 当前 Sprint / Backlog / 用户最新指令中明确指派的工作 | TodoWrite 清单 / Issue / Task ID |
| D2 | **需求** | 需求规格文档中明文规定的功能点 | PRD / FRD / User Story / FR-编号 |
| D3 | **范围** | 项目阶段范围（IN/OUT 矩阵） | MVP 定义 / Phase 划分 / Scope 文档 |

#### 8.8.2 检查时机（强制）

| 时机 | 是否必做 |
| --- | --- |
| 每完成一个原子改动（commit / 写完一个文件 / 一个函数 / 一个类） | ✅ 必做 |
| 完成 TodoWrite 中一项 todo | ✅ 必做 |
| 跨越 Phase / Module / Layer 边界时 | ✅ 必做 |
| 长时间无检查（> 30 分钟） | ✅ 必做 |
| 用户在对话中改了方向 / 加了新需求 | ✅ 立即重做 |
| AI 准备"顺手加"任何东西之前 | ✅ 必做 |

#### 8.8.3 偏移类型与判定

| 类型 | 含义 | 典型信号 | 处理 |
| --- | --- | --- | --- |
| **任务偏移** | 写到一半开始做别的事 | 当前任务 A 还在进行，代码却处理 B | 立即停止，回到 A 或询问是否切换 |
| **需求偏移** | 实现没有需求编号对应 | 找不到对应的 FR / Story / 验收点 | 立即停止，回退或按 §3 询问 |
| **范围偏移** | 实现了范围矩阵 OUT 的功能 | 命中"不做清单" / OUT 档 / V1.5+ 功能 | 立即停止，删除代码或按 §3 询问 |
| **AI 想象** | 凭"合理"加规范没说的功能 | 加缓存 / 加日志 / 加重试 / 加抽象层，需求未提 | 立即停止，**强制 §3 询问**，不允许自决 |
| **接口偏移** | 改了已定义的接口（API 路径 / 表名 / 字段 / 事件名） | 与已锁定的接口契约不一致 | 立即停止，按 §3 询问 |
| **技术偏移** | 引入项目技术栈外的库 / 框架 | 用了规范技术栈以外的依赖 | 立即停止，按 §3 询问 |

#### 8.8.4 标准动作（流程图）

```
完成一个原子改动
       │
       ▼
自问 3 问（必须全部答"是"才能继续）：
  1. 这段代码对应 D1（任务）吗？ → 答不出具体任务 → 停
  2. 这段代码对应 D2（需求）吗？ → 找不到 FR/Story → 停
  3. 这段代码在 D3（范围）内吗？ → 命中 OUT 清单 → 停
       │
       ├── 任一答否 / 答不出
       │        │
       │        ▼
       │   立即停止当前编辑（不要 commit、不要继续写下一行）
       │        │
       │        ▼
       │   按 §3 用 AskUserQuestion 询问（用 §4 模板）
       │        │
       │        ├── 用户确认属于合理扩展 → 追加 ADR + 更新规范 + 继续
       │        ├── 用户要求回退 → 立即删除 / git restore
       │        └── 用户说"你自己决定"（仅非红线场景）→ 记 ADR 后继续
       │
       └── 全部答"是" → 继续
```

#### 8.8.5 红线（与本规范其它红线同级）

| # | 红线 | 含义 |
| --- | --- | --- |
| A1 | **禁止写完不复盘** | 任何原子改动完成都必须做 §8.8.4 的 3 问 |
| A2 | **禁止带偏移继续** | 发现偏移后不允许"先这样稍后再调" / "等会儿再补测试" |
| A3 | **禁止"看似合理"** | "听起来很合理"不是通过依据；**只有规范明文才是** |
| A4 | **禁止省略 AskUserQuestion** | 发现偏移必须按 §3 询问，不能自我决定（违反 SP4 同样违规） |
| A5 | **禁止偏移后静默 commit** | 偏移未解决前禁止任何 `git commit`（叠加 §1.3 P1） |

#### 8.8.7 自检清单（每完成原子改动后追加 3 问，与 §8.6 配套）

- [ ] **D1 任务**：这段代码对应哪条 Task / Issue / Todo？（写出来）
- [ ] **D2 需求**：这段代码对应哪条 FR / Story / 验收点？（写出来）
- [ ] **D3 范围**：这段代码在 MVP / Phase / IN 矩阵内吗？（写"是"或"否"）
- [ ] **AI 想象检查**：我有没有"顺手加"规范没有的东西？（如果犹豫 → 停）

#### 8.8.8 项目无关性说明（**重要**）

本节是**模板化规范**，故意**不引用任何具体项目**：

| 故意不引用的内容 | 原因 |
| --- | --- |
| 具体项目名（如 AsyncStarterAgent） | 任何项目都用得上 |
| 具体文件名（如 requirement-spec.html） | 你项目里可能叫 PRD.md / FRD.md / Spec.md |
| 具体 FR 编号（如 FR-B01） | 你项目里可能叫 US-001 / STORY-12 / AC-3 |
| 具体业务术语 | 你项目可能是电商 / 金融 / 工具 / 游戏 |

**移植步骤**（把 §8.8 复制到任何新项目时）：
1. 把 §8.8.1 表格中"映射示例"列替换为你项目对应的概念
2. §8.8.2 / 8.8.3 / 8.8.4 / 8.8.5 / 8.8.7 全部**直接复用**，无需修改
3. §8.8.6 中对本规范其它章节的引用（§1.1 R1 等）按新项目编号调整

#### 8.8.9 与 §8.4 / §8.6 的协同

- **开始前**：§8.6 检查"该调的 Skill 调了没"（特别是 `brainstorming` / `TDD`）
- **过程中**：每完成原子改动 → §8.8.7 3 问
- **完成后**：§8.6 检查"完成前是否跑过测试 + lint + diff"
- **提交前**：§8.8 + §8.6 双重通过 → 才能问用户是否 commit

## 9. 违规处理

如果 AI 发现自己已经越界（例如已写出规范外的代码）：

1. **立即停止**后续编辑
2. **主动告知**用户："刚才的改动超出了 [具体规范] 范围，原因是 [XXX]"
3. **不要试图隐藏**，直接展示越界代码
4. **等待用户决定**：回退 / 修改 / 保留并补充规范
5. **追加 ADR** 记录此次事件，作为后续规避参考
